# 部署与演示

## 本地运行

安装步骤见开发说明。启动入口：

```powershell
.\start.bat
# 或
.\.venv\Scripts\python.exe app.py
```

默认访问 `http://127.0.0.1:5000`，使用 Waitress 服务。`start-dev.bat` 使用开发服务器但不启用交互式调试器。启动脚本不会结束其他 Python 或 Ollama 进程。端口占用时修改 `BIOKB_PORT`，不要终止不属于本项目的服务。

桌面窗口可通过 `start.bat gui` 启动。`build.bat` 提供 PyInstaller 构建入口，输出 `dist/BioKB.exe`；源码运行验证不等于已验证该可执行文件分发，应在目标机器单独验收。

## 配置模型

默认 `BIOKB_LLM_BACKEND=disabled`，问答展示相关原文。使用本地模型时设置后端为 `ollama`，服务地址为实际 Ollama 地址，并填写已经部署的模型名。向量后端独立配置为 `ollama`，使用支持 embedding 的模型。

OpenAI 兼容服务使用 `openai_compatible`，`BASE_URL` 指向服务实际 API 根地址，例如带 `/v1` 的地址，程序分别追加 `/embeddings` 或 `/chat/completions`。模型名、密钥和网关支持能力以实际部署为准。不同任务可使用不同服务。

更换向量模型后执行：

```powershell
.\.venv\Scripts\python.exe -m biokb reindex
```

重建期间旧索引保留。索引和当前模型不一致时，向量/混合检索会明确报错，BM25 仍可使用。

## 系统变量与兼容服务

可在 `.env` 的 `BIOKB_LLM_API_KEY_ENV`、`BIOKB_EMBEDDING_API_KEY_ENV`、`BIOKB_RERANKER_API_KEY_ENV` 填写已有环境变量的名称，密钥值不需复制。优先级为专用 API_KEY 值、当前进程引用变量、Windows 用户/系统变量。修改后重启应用。

本机已验证硅基流动 `https://api.siliconflow.cn/v1`，分别配置 Qwen/Qwen3-Embedding-8B、Qwen/Qwen2.5-72B-Instruct、BAAI/bge-reranker-v2-m3；生成设置 `BIOKB_LLM_RESPONSE_FORMAT=json_object`，重排序设置 `BIOKB_RERANKER_BACKEND=compatible`。其他兼容服务需单独验证，默认响应格式 text 不要求 JSON mode 能力。

`python scripts/check_models.py --output output/model_check.json` 会真实调用已配置服务，报告无凭据。接口成功不代表回答事实正确。

容器无法读取 Windows 注册表或未传入的宿主系统变量；使用容器时需要在运行环境安全注入对应变量，不能仅复制宿主变量名便假定鉴权可用。

## 现有语料迁移

```powershell
.\.venv\Scripts\python.exe -m biokb import-legacy
```

从旧项目生物语料目录读取文献，默认写入 `data/biokb/knowledge.sqlite3`。同名 JSON/TXT 以含元数据的 JSON 为准；按原始文件哈希避免重复导入。旧数据库、图元和 GraphRAG 工作区保持不变。

自定义语料：`python -m biokb import <文件或目录>`。批量导入报告区分已导入、重复和失败；存在失败返回非零退出码。

## 数据备份与恢复

运行数据目录包含 SQLite 数据库及其 WAL 文件、原始文件归档。建议停服后整体复制 `BIOKB_DATA_DIR`；运行中只复制 `.sqlite3` 文件可能遗漏 WAL 中的更新。凭据文件单独保管，不进入源码压缩包。

恢复时停止服务，将备份的数据目录恢复到明确的目标位置，检查配置路径，再执行 `biokb doctor` 验证索引指纹。当前没有自动删除原始归档文件的清理任务。

## 网络访问

默认仅本机访问。需要监听其他地址时必须设置 `BIOKB_API_TOKEN`，浏览器通过访问验证面板输入令牌。远程部署还需 TLS、反向代理和访问管理。该令牌是单实例共享令牌，不等同于多用户身份与角色权限。

Docker 示例位于 `deploy/`，使用独立数据卷和显式访问令牌。反向代理模板必须按实际域名和 TLS 环境配置。仅提供构建文件不代表已完成生产部署验证。

在根目录创建 `.env` 并设置非空 `BIOKB_API_TOKEN` 后运行：

```powershell
docker compose --env-file .env -f deploy/compose.yaml config --quiet
docker compose --env-file .env -f deploy/compose.yaml up -d --build
docker compose --env-file .env -f deploy/compose.yaml logs --tail 100
```

容器内部监听 `0.0.0.0:5000`，宿主机默认仅发布 `127.0.0.1:5000`；可通过 `BIOKB_PUBLISHED_PORT` 改宿主端口。容器使用 UID 10001 运行，数据存于独立命名卷 `biokb_data`，首次为空，不自动包含工作机的任何文献或语义索引。需要现有数据时应停服并通过经过核对的备份恢复流程导入。不要执行删除数据卷的命令作为日常重启方式。

`.env` 仅在运行时读取，不复制进镜像。外部模型地址必须是容器可访问的地址；容器内的 `127.0.0.1` 指向容器自身。配置未设置令牌时，Compose 的必填变量校验会拒绝启动。文件语法依据 [Dockerfile 官方说明](https://docs.docker.com/reference/dockerfile/) 和 [Compose 变量说明](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

`deploy/keyanhuitu.nginx.conf` 保留旧文件名便于定位，内容已改为无公网地址的本机模板，监听 `127.0.0.1:8080`。远程域名代理必须保留原始 Host，并将应用配置为网络监听且设置令牌；同时通过防火墙限制应用端口，只从反向代理访问，单独配置 TLS。模板未经实际 Nginx 启动验收。

## 源码分发

```powershell
.\pack.bat
.\.venv\Scripts\python.exe scripts/verify_package.py output\distributions\实际生成的源码包.zip
```

源码包位于 `output/distributions/`，按白名单包含当前代码、中文主线文档、测试、部署与验证脚本，附带 `SOURCE_MANIFEST.json`。原始语料、数据库、真实 `.env`、旧实现、旧归档和本机验证输出不随包分发；包内安装说明与文档链接单独检查。旧文档入口文件不混入源码包，避免指向被排除的归档。

## 健康检查与常见问题

`GET /api/health` 只检查 Web 服务可用，不代表模型已连接。`biokb doctor` 检查配置与索引一致性，也不会自动调用收费服务。

Windows 可执行 `powershell -NoProfile -File scripts/health_check.ps1` 检查页面及四个知识库接口；启用认证时，先在该终端设置 `BIOKB_API_TOKEN`。脚本使用 UTF-8 BOM，兼容 Windows PowerShell 5 的中文解析。

- 问答显示原文：生成后端未启用，或模型调用失败后明确降级。
- 语义检索效果弱：检查是否仍使用哈希基线，及问题/文献语言是否匹配。
- PDF 入库失败：扫描件需要先 OCR；损坏文件或加密限制应先处理。
- 文档重复：相同原始字节只入库一次。
- 任务重启后中断：历史页显示最近任务，支持重新提交；超过最近 100 条保留范围时，完成结果仍可到文献、问答或评估记录中检查。部署只启动一个应用进程，不能将单机任务恢复当作分布式队列使用。
